# تسليم الأسبوع الرابع: دمج المخاطر والتقرير

## ما أُضيف

- حساب محلي حتمي لـCVSS 3.1 Base من المتجه الذي يختاره المقيّم؛ لا يُقبل إدخال درجة يدوية بديلة عن الحساب.
- حقولا `business_impact` و`owner` الاختياريان، مع بقاء الخطورة اليدوية منفصلة عن CVSS.
- تحميل ملفات Finding JSON من مجلد واحد أو عدة مجلدات، مع تجاهل ملفات التغطية وإظهار الملفات غير الصالحة.
- الأمر `/report` لإنتاج تقرير Markdown أولي وسجل مخاطر CSV تحت `reports/`.
- التقرير يقسم النتائج إلى `human_verified` و`needs_human_review`؛ النتائج غير المؤكدة لا تدخل الملخص التنفيذي.
- اختبارات ببيانات اصطناعية فقط؛ لم يُرسل أي طلب إلى موقع أو مختبر.
- استُكملت تغطية Member 3 في 3.C بأربع مهارات: SQLi وSSRF وPath Traversal وFile Upload. ملفات `payloads/` مراجع آمنة فقط، وتشمل canary نصيًا غير نشط.
- أُعيدت كتابة مهارة SSRF لتقتصر على مراجعة الشيفرة وفحص واحد بوجهة يملكها الفريق وبعد تأكيد النطاق؛ لا تشمل الوصول الداخلي أو metadata أو تجاوز المرشحات أو سحب البيانات.

## طريقة دمج ملفات الفريق

ضع ملف JSON جانبيًا لكل Finding في مجلد العضو، ثم نفّذ من مجلد المشروع:

```text
/report member-one/findings,member-two/findings,member-three/findings
```

يقرأ الأمر ملفات `.json` الموجودة مباشرة داخل كل مجلد. لا يقرأ ملفات Markdown ولا يدخل المجلدات الفرعية تلقائيًا. تُتجاهل ملفات `coverage-*.json`. الملفات المعطوبة أو المخالفة لمخطط Finding تُذكر في قسم التحذيرات بدل اعتبارها نتائج.

إذا كان ملفان يحملان النتيجة نفسها، راجع التكرار يدويًا؛ لا يحذف النظام النتائج المتشابهة تلقائيًا. استخدم معرّفات ثابتة وواضحة لتسهيل التنسيق بين أعضاء الفريق.

## CVSS والأثر التجاري

يمرر المقيّم `cvss_vector` إلى أداة `confirm_finding` فقط بعد اختيار قيم AV وAC وPR وUI وS وC وI وA. تحفظ الأداة المتجه والنتيجة المحسوبة في الكائن `cvss` داخل JSON وفق `schemas/finding-v1.schema.json`. مثال حسابي اختباري، وليس Finding للمشروع:

```text
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H -> 9.8 Critical
```

تُعاد عملية الحساب عند تحميل ملف JSON؛ لا يعتمد التقرير على الدرجة المخزنة إذا خالفت المتجه. هذا الإصدار يحسب Base فقط، ولا يحسب Temporal أو Environmental. تُعرض الخطورة اليدوية وCVSS في عمودين منفصلين؛ يجب على المراجع تفسير أي اختلاف. إذا لم يوجد متجه، تظهر الدرجة كـ`Not assessed`.

لا يستنتج HackerClaw أثرًا تجاريًا من الخطورة التقنية. املأ `business_impact` بمعلومة يدعمها سياق العمل، وإلا يعرض التقرير `Not assessed`. لا تغيّر `verification_status` إلى `human_verified` إلا بعد إعادة اختبار بشرية ضمن نطاق مصرح به.

## الملفات الناتجة

- `reports/pentest-report-<time>.md`: مسودة أولية، نطاق وتواريخ التقييم موضّحان كغير متوفرين ما لم يضيفهما الفريق.
- `reports/risk-register-<time>.csv`: سجل موحد قابل للفتح في أدوات الجداول، ويضم المصدر والحالة والخطورة اليدوية وCVSS والأثر التجاري.

تُحجب أنماط شائعة من الأسرار تلقائيًا، لكن على الفريق مراجعة الأدلة والروابط قبل مشاركة التقرير؛ لا يغني ذلك عن التنقيح اليدوي. التقارير محلية، ويستثنيها `.gitignore` لأنها قد تتضمن بيانات تقييم حساسة.

## التحقق

```sh
npm run ci
```

الاختبارات تستخدم مجلدات مؤقتة وملفات وهمية. عند تشغيله على نتائج حقيقية، ينبغي إضافة النطاق والتواريخ والاستبعادات ومراجعة كل نتيجة قبل توزيع التقرير. لا توجد Finding حقيقية متاحة في هذا التسليم، لذلك لا يتضمن التقرير التجريبي ادعاءات عن نظام فعلي.

## مهارات Member 3

المجلدات `skills/sqli/` و`skills/ssrf/` تتضمن ملفات إرشاد تحت `payloads/` ليقرأها `read_payloads`؛ لا تحتوي قوائم حقن عامة. أضيفت `skills/path-traversal/` لمراجعة احتواء المسارات، و`skills/file-upload/` لمراجعة التحقق والتخزين والصلاحيات، مع canary نصي خامل فقط. التحقق الفعلي من النتائج يبقى على المختبر البشري داخل بيئة مصرح بها؛ لم يُختبر هدف في هذا التسليم.
