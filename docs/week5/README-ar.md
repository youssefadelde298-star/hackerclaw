# Week 5: إعادة الاختبار وتقييم AI والعرض النهائي

## الهدف

إغلاق دورة العمل: إعادة اختبار Findings سبق أن تحقق منها الفريق، قياس فائدة AI على مجموعة حالات ثابتة، معالجة مشكلات التكامل، وإعداد تقرير وعرض نهائيين. لا توجد Finding لهدف الفريق أو نتائج محلية لـQwen/Llama في الملفات المتاحة؛ لذلك هذه الحزمة تقدم خطة وقوالب ولا تدّعي اكتمال تلك التجارب.

## 1. إعادة الاختبار

استخدم [قالب مصفوفة إعادة الاختبار](retest-matrix-template.csv)، وصفًا لكل Finding على حدة. قبل الإعادة:

- تحقق من أن النطاق والتفويض ما زالا ساريين وأن حساب المختبر مخصص للاختبار.
- أعد تنفيذ الخطوات المكتوبة يدويًا داخل المختبر فقط، وسجل النتيجة والأثر قبل وبعد.
- لا تعاود تغيير حالة Finding إلا بعد مراجعة بشرية للدليل الجديد.
- إذا لم تتوفر Finding أصلية، اكتب `Not available - no verified finding supplied` في تقرير الحالة؛ لا تصنع Finding لاختبار القالب.

الحالات المقترحة: `not_started`, `reproduced`, `fixed`, `partially_fixed`, `not_reproduced`, `blocked`. اشرح أي تغير في البيئة أو الإصدار.

## 2. تقييم AI

سجل القياسات في [قالب تقييم AI](ai-evaluation-template.csv). استخدم الحالات نفسها والـprompt نفسه لكل نموذج، وعلى جهاز الفريق نفسه. نفّذ ثلاث مرات على الأقل لكل حالة، وافصل زمن التشغيل البارد عن الدافئ عند الحاجة. استخدم بيانات اصطناعية أو منقحة لا تتضمن أسرارًا.

المقاييس التي يجب أن يتفق عليها الفريق مسبقًا:

- صحة القرار مقابل إجابة مرجعية معروفة، وليس انطباعًا عامًا فقط.
- عدد الاقتراحات الصحيحة والخاطئة والممتنعة عند نقص الدليل.
- نجاح استدعاء الأداة عندما تتطلب الحالة ذلك، مع عدم تنفيذ طلب اختبار غير مصرح به.
- زمن الاستجابة الوسيط، وجودة المخرجات وفق rubric ثابت من 1 إلى 5.
- نسبة الاقتراحات التي أكدها مراجع بشري. لا تسمَّ هذه النسبة Accuracy من دون مجموعة مرجعية كاملة.

سجّل اسم النموذج والـtag والـruntime والعتاد وإصدار الـprompt والنتيجة لكل تشغيل. لا تضع نصوص الطلبات أو مخرجات حساسة في CSV؛ استخدم معرفات حالات فقط. توثيق Qwen السابق فحص تشغيل واحد في بيئة مؤقتة، وليس هذه المقارنة.

## 3. التقرير والتكامل

- اجمع Findings JSON من أعضاء الفريق عبر `/report`، وراجع الملفات المرفوضة والتكرارات يدويًا.
- استخدم قالب [التقرير النهائي](final-report-template-ar.md) وأكمل النطاق والتواريخ والاستثناءات والمخاطر والأثر التجاري من بيانات الفريق فقط.
- ضع النتائج غير المؤكدة في قسم منفصل. لا يظهر في الملخص التنفيذي إلا ما تحققت منه يدويًا.
- راجع أن بيانات CVSS 3.1 Base مبنية على متجه اختاره المقيّم، وأن الأثر التجاري غير مستنتج من AI.
- افحص أسماء المستودع وأصول الإصدار والمثبتات قبل نشر إصدار. أضيفت اختبارات اتساق للأصول وفحوصات صياغة للمثبتات، لكن فحوصات CI لم تُشغّل بعد هنا، ولا تختبر فحوصات npm تنزيل أصول GitHub أو تثبيتها فعليًا على Windows/macOS.

## 4. العرض النهائي

استخدم [نص العرض](demo-script-ar.md). يمكن تنفيذ عرض برمجي ببيانات اصطناعية، لكن لا تقدمه على أنه تقييم تطبيق حقيقي. إذا لم يقدم الفريق هدفًا مصرحًا ونتائج موثقة، اذكر أن demo يشرح سير العمل وأن تقييم الهدف وإعادة الاختبار ما زالا معلقين.

## الحالة الحالية

لا توجد نتائج Retest أو مقارنة محلية Qwen/Llama أو تقرير تقييم فعلي لهدف الفريق ضمن الملفات التي راجعناها. لا يمكن اعتماد «لا توجد نتائج» بوصفه حكمًا بأن التطبيق آمن. كما أن المقترح يذكر طبقة Python، بينما التنفيذ الحالي TypeScript/Node.js؛ يجب توثيق قرار المشرف قبل وصف المتطلب بأنه مكتمل.

## التحقق الآلي في هذه النسخة

- التاريخ: 2026-11-18 UTC.
- البيئة: Linux، Node.js 22.23.2، npm 10.9.2.
- `npm ci` ثم `npm run ci`: نجح التثبيت النظيف، وTypeScript، وBiome على 159 ملفًا، و695 اختبارًا عبر 68 ملفًا، وبناء esbuild وفحوصات تشغيل CLI وMCP المبنيين.
- `npm audit`: خمسة تنبيهات عالية في سلسلة اعتماديات التطوير عبر `picomatch`. `npm audit --omit=dev`: صفر تنبيهات. يقترح الإصلاح القسري خفض Vitest إلى 3.1.4 كتغيير كاسر؛ لم يُفرض.
- اجتاز `sh -n install.sh` و`bash -n scripts/build-binaries.sh` محليًا، وأضيف فحص محلل PowerShell وفحوصات صياغة لأنظمة متعددة في CI، لكن سير عمل GitHub وأصول الإصدار والتثبيت الفعلي لم تُختبر هنا. لم يُشغّل نموذج على جهاز الفريق أو أي هدف ويب في هذه البيئة.
