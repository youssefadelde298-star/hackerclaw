# Cross-Site Request Forgery (CSRF) Playbook

Use only for the exact application, routes, and test accounts the user is authorized to assess. A human tester owns scope, reproduction, and the final finding decision. This playbook evaluates whether an application correctly proves request intent for an authenticated, state-changing action; it does not create attacker pages, target other users, or attempt account takeover.

## 1. Scope and safety

- Before sending a request, confirm the authorized host, exact route, method, test account, lab-owned state-changing fixture, expected safe outcome, browser, and request limits. If any part is unclear, ask once with `ask_user` and wait.
- Use a user-provided, sanitized baseline request. Redact cookies, bearer tokens, passwords, personally identifiable information, and production records before analysis or saving.
- Restrict verification to a documented, reversible training action on the tester's own account—such as a lab-owned display preference—never passwords, email addresses, recovery details, funds, roles, permissions, API keys, security settings, or records belonging to another person.
- Do not host or deliver a cross-site page, use an iframe, force browser navigation, manipulate request headers/cookies, weaken/reforge tokens, exploit CORS, alter referer behavior, or test bypasses. Do not automate requests or use batches.
- Stop if the action is not reversible, the response exposes sensitive data, the request crosses scope, browser behavior is unexpected, or an unapproved user/session could be affected.

## 2. Recognize the security model

CSRF relies on a browser automatically attaching ambient authentication—commonly a session cookie—to a request for an already authenticated site. A secure state-changing endpoint should require evidence that the request was intentionally generated by the legitimate application, not merely that the browser has a valid session.

Key controls to review:

- **Synchronizer token:** server generates an unpredictable token, associates it with the user/session or intended operation, and validates it before the state change. It is commonly placed in a form field or sent in a custom header.
- **Double-submit pattern:** a cookie value and separately submitted value are compared. It needs careful integrity and binding design; it is not equivalent to a server-side session-bound synchronizer token.
- **SameSite cookies:** `Strict`, `Lax`, and `None` affect when cookies accompany cross-site navigation and embedded requests. They are useful defense in depth, not a replacement for per-request intent validation on sensitive changes.
- **Origin/Referer validation:** an exact, allowlisted origin check can add defense in depth. Missing, partial, substring, or permissive validation is not a substitute for a robust token policy.
- **Method and content type:** changing a route from POST to GET does not make a state change safe. State changes should not be exposed through GET, and security checks must apply consistently to every accepted representation.
- **Browser boundaries:** the same-origin policy limits a foreign page's ability to read protected responses. It does not by itself prevent an authenticated request from being sent, which is why server-side intent checks matter.

## 3. Safe manual test workflow

Before any request, read `read_payloads(skill="csrf", file="lab-cases.txt")`. It contains only scope and fixture rules; it intentionally ships no cross-site request templates, bypasses, or token-manipulation instructions.

1. Capture a normal baseline request for the approved reversible lab action. Record endpoint, method, expected state transition, token/header/origin-related fields present, status, a short redacted response excerpt, and the before/after state.
2. Inspect the normal application flow and server response to document the anti-CSRF design: where the token originates, how it is submitted, whether state changes are reachable through alternate methods/routes, and the session-cookie attributes. Treat this as design evidence, not proof of a flaw.
3. Use the lab's approved negative-control fixture only, if it exists. A safe negative control is one that stays entirely within the tester's own authenticated application flow and confirms that a missing or malformed *lab fixture* intent value is rejected before any state change. Do not substitute or reuse another user's token, edit cookies/headers, or try to bypass validation.
4. Confirm the result by checking that the approved state did not change and that the application issued the expected rejection. If a token is accepted unexpectedly, do not escalate into bypass attempts; stop and preserve the redacted evidence.
5. Restore the lab fixture to its original value through the normal UI if it changed. Record the cleanup and verify the final state.
6. Stop once the smallest safe retest yields repeatable evidence. If the lab does not offer a reversible action or approved negative control, report the review as design-only or unconfirmed.

## 4. Evidence, remediation, and review

- Save sanitized baseline and negative-control request/response separately. Record the one intended variation, observed rejection/acceptance, before/after state, cookie attributes visible in the response, and cleanup result. Remove all secrets.
- A missing or weak visible control is not automatically exploitable; report the actual observed behavior and scope limits. Do not claim account takeover, financial loss, privilege change, or impact on other users unless independently demonstrated in a separately authorized exercise.
- Recommend a server-generated, unpredictable synchronizer token bound to the authenticated session and, where appropriate, the intended action; validate it before changing state, reject absent/invalid tokens consistently, and avoid state-changing GET routes.
- Add exact origin checks as defense in depth, configure session cookies with `Secure`, `HttpOnly`, and an appropriate `SameSite` value, and require re-authentication or step-up confirmation for high-risk changes.
- Draft a finding only from evidence actually observed. Keep AI output at `verification_status: needs_human_review`; a human must independently repeat the safe test and review evidence before changing status.
- Call `confirm_finding` only after the tester explicitly confirms the manual retest and evidence. The tool's human approval prompt must be accepted before saving.

## 5. Source-note boundaries

The supplied notes provide useful explanations of cookies, sessions, request intent, tokens, SameSite, Origin/Referer, SOP, CORS, framing, and the consequences of sensitive state changes. The following source-note material is intentionally out of scope for this skill: changing email/password or recovery data, financial actions, role/permission changes, forcing requests from an attacker-controlled page, iframe or form delivery, token theft/reuse, double-submit manipulation, HTTP header injection, referer manipulation, cross-origin response reading, XSS chaining, bypassing token or method checks, and targeting third-party users. Do not turn these into proof steps or reusable examples. A separate, deliberately isolated lab curriculum and human approval are required for any such exercise.
